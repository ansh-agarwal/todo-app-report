What people keep asking for, how the incumbents are built, where the feeling of speed actually comes from, and the architecture that follows.

I What people
ask for

Six requirements, in their own words

Everything after this part is machinery. This part is the brief. Each ask is recorded verbatim, with what it actually means and what it forces on us — because a requirement that doesn't constrain a decision isn't a requirement, it's a wish.

Most repeated ask

"Capture in under 5 seconds without deciding where it goes."

Reading
The filing is the tax, not the typing. Five seconds is a real threshold — above it, consistency collapses and the tool stops being used at all.
Forces
No mandatory destination at capture. An unfiled object is a first-class, valid state, not an error to resolve later. Nothing on that path may block — not a sync round-trip, not an index write, not a modal asking which project.
Unsolved — the frontier

"Turn my note into a task without re-typing it."

Reading
Notes and tasks are the same object at different moments in its life. The boundary between them is imposed by app architecture, not by how anyone thinks.
Forces
One object type with a task facet, not two stores with an import between them. Promotion is a field appearing in frontmatter, not a copy operation. Nobody has delivered this well, which is exactly why it's worth the effort.
ADHD-specific

"Don't make me manage a system on top of managing my life."

Reading
More choice is the problem, not the cure. Every configurable surface is maintenance work handed back to someone who came here to offload it.
Forces
Our AI must reduce visible complexity, not add knobs. The test for any feature: does it remove a decision, or add a setting? This is Things 3's calm-by-subtraction with a sharper edge — the audience most helped by the tool is the one least able to absorb its configuration.
Retrofit debt

"Work as well on mobile as on desktop."

Reading
Recurs for Notion, Evernote and OneNote alike. It is architectural debt none of them can cheaply retrofit, because mobile was a port of a desktop premise.
Forces
Shared core, native shell, mobile designed against the same core from day one. This is the requirement that validates the split in Part IV — and the one Obsidian's WebView answer fails.
Norm shift

"Don't lock AI behind a subscription when I already pay for the AI myself."

Reading
Bring-your-own-key has moved from niche to expected. Charging a margin on inference the user is already buying now reads as a toll.
Forces
BYOK as a first-class path, alongside the local model. It also constrains the pricing thesis: if raw inference is the user's own, the paid tier has to be judgment, ranking and timing. Which is precisely where Smart Connections' paywall already sits.
Trust

"Stop breaking sync between your own apps."

Reading
Trust in sync is fragile even among giants with far more engineering than us. One silent conflict costs more goodwill than a year of features earns.
Forces
Sync state is visible and inspectable, never opaque. And files on disk are the escape hatch — when sync does fail, the failure is an inconvenience the user can resolve in a folder, never data loss.
How the brief lands against the architecture

Four of the six are already answered by choices made on other grounds — atomic objects, native shell over shared core, calm by subtraction, files-as-canonical. That agreement is a good sign, not a coincidence. Two are genuinely new constraints: note-and-task as one object with two facets, and BYOK as a first-class path. Both are carried into Part IV.

II How Obsidian
is built

The vault is a folder, and the speed is a cache

Files are the database

Most note apps store notes as rows and render them as documents. Obsidian inverts it: the .md file on disk is the record. No SQLite, no server, no relational schema. Sync becomes file sync. Export becomes nothing at all — you already have the folder.

The cost is that you have no query engine. Text isn't queryable. Everything below is the machinery built to get that back.

Frontmatter: an optional schema

A YAML block fenced by --- at the very top of the file gives each note a small machine-readable record without leaving markdown.

---
status: draft
tags: [research, competitive]
due: 2026-08-14
---

# Obsidian teardown

Files are the database. The speed secret is the cache...

It is optional, and that word carries weight. A note without frontmatter is perfectly valid — it opens, searches, and links fine. So the store is schemaless: a field may be absent, may be missing on half the vault, may hold a hand-typed priority: high where a number was expected. Validation is a read-time job, on every file, forever.

Consequence for our writer

Treat absent as a valid state with a sensible default, never an error. And when writing a file back, preserve unknown frontmatter keys and their order — other tools put fields there. A naive parse-and-reserialize eats them silently, and that is the bug class that makes people stop trusting a tool.

The metadata cache

Parsing markdown is expensive. If every query re-read and re-parsed 5,000 files, every interaction would take seconds. So each file is parsed once into a structured record held in memory. Queries hit that record; raw markdown is never re-parsed at query time.

Three properties hold it together: parse-once/query-many amortises the cost, incremental invalidation re-parses exactly one file per edit, and a filesystem watcher means it's event-driven rather than burning CPU on a polling loop.

The property that makes it safe

The cache is derived state, not source of truth. It persists to IndexedDB for cold start, but delete it and it rebuilds from disk. That is precisely what licenses aggressive caching without risking data. Same discipline as a search index over a git repo.

What a cached record actually holds

FieldExtracted from
frontmatterYour YAML fields — the part you define
links[[wikilinks]] with position offsets
embeds![[transclusions]]
tagsInline #tags in the body
headingsText, level, position
sectionsBlock-level layout map of the document
listItemsBullets, indent depth, task checkbox state
blocks^block-id anchors

Vault-wide, it also keeps a file registry (path, size, mtime) and a resolved/unresolved link graph that powers backlinks. What it does not keep is note body text — positions are offsets pointing back into the file, so opening a note is still a real disk read.

Two tiers, and the recall they buy

Metadata query

  1. tags · links · frontmatter · headings
  2. served from RAM
  3. no disk touched

Instant. Scan over in-memory structs.

Full-text search

  1. "find the word membrane"
  2. reads file contents
  3. separate path entirely

Noticeably slower. Bodies aren't cached.

The design rule that falls out: anything you will filter on frequently belongs in frontmatter, so it stays in the fast tier.

Optional frontmatter costs recall, never speed. If ten notes are genuinely drafts but only seven carry status: draft, the query returns seven — fast and correct, at 70% recall. The three untagged drafts are invisible, not slow. Recovering them means a full-text fallback, semantic search, or enforcing the field on write.

Invalidation: two mechanisms

  • While running — a filesystem watcher fires on create, modify, delete, rename. On modify, one file is re-parsed, its record swapped, and a changed event emitted so views and plugins refresh. Delete drops the record and flips inbound links to unresolved.
  • On startup — each persisted record's mtime and size are compared against disk. Match, trust the cache. Mismatch, re-parse just that file.

Edits made while the app was closed — a git pull, a sync, another editor — are caught by the mtime check, not the watcher. That is the whole reason external editing works at all.

The decision that bought the speed

Roam and Logseq make the block the addressable unit: every bullet gets an ID, can be referenced, transcluded, queried. More expressive, and a performance trap. A vault of 5,000 notes becomes roughly 500,000 nodes in a densely connected reference graph — edit one bullet and you must work out which of half a million derived records just went stale.

Obsidian's unit is the file. Five thousand nodes. Edit one, invalidate one. The claimed ~100× faster load is mostly this: not clever engineering, but a smaller problem chosen up front. The trade is real — you can't cheaply ask "which bullets mention X". Block refs got bolted on later and stayed second-class, because the architecture doesn't centre them.

III Where fast
comes from

Two case studies, and neither one is about rendering tricks

The keystroke path

Sublime's snappiness isn't one trick. It's the absence of a browser.

Sublime — native C++

  1. input event
  2. edit buffer
  3. GPU repaint

Three steps. Sub-millisecond, every frame, no variance.

Obsidian / VS Code — Electron

  1. keystroke
  2. DOM event
  3. JS handler
  4. style recalculation
  5. layout
  6. paint
  7. composite

Plus GC pauses landing at random.

What you are actually feeling

Even when the Electron path is fast, it is variably fast — and the eye reads variance as lag. The perceptual targets are input latency under ~10ms, no dropped frames while scrolling, and instant window open because nothing boots a runtime.

And why opening a folder is instant

Different question, three answers, and the first is the big one.

a

Sublime opens before it indexes

The UI is usable immediately; symbol indexing runs on background threads and trickles in. What reads as "instant" is Goto Anything — which needs only a directory listing, not file contents. Milliseconds for 50,000 files.

b

It does far less per file

Its index is symbol definitions only — a shallow single-pass scan keeping name and line. Obsidian does a full markdown parse per file, then a second pass resolving every link across the vault to build the graph.

c

Threads

Sublime is C++ across all cores. Obsidian's parse is JS on essentially one thread, then writes each record to IndexedDB — structured-clone overhead on every file.

Takeaway for us

Open instantly, index lazily, parallelise the parse, and let features light up as the index fills. Blocking on a full index before the app is usable is a choice, not a requirement.

Purpose-built primitives on the hottest path

The deeper answer to "why is it like that" is that Sublime replaced the generic component wherever a generic component sat on the critical path.

PrimitiveReplacesBought
SkylineQt / platform widget toolkitFull control of the frame; no toolkit layout pass between input and paint
sregexPCRE / std regexTests many patterns in one pass — syntax highlighting matches hundreds of rules per line
LevelDB symbol indexRe-scanning on demandPersisted across launches, so the work survives the process
GPU renderingCPU rasterisationScroll and repaint stay at frame rate on large files
The principle worth stealing

Do the work once, ahead of time, reuse it. That is the same shape as parse-once/query-many in Part II — Obsidian and Sublime arrived at it independently. For us it means a bespoke, persisted local index built for the capture-and-retrieval hot path, not a general store we query around.

The part we cannot copy

Sublime afforded years of custom-toolkit work because it was patient, profitable and never took venture money. We are not. Default to native toolkits; go bespoke only where profiling proves the primitive is the differentiator. Building our own Skyline in year one would be borrowing their answer without their balance sheet.

Things 3: the same feeling, none of the same machinery

Worth studying precisely because it is not exotic rendering. Things 3 feels instant because it is local-first with background sync — the UI never blocks on a network round-trip. Writes land locally and return immediately; replication is something that happens afterwards, out of the user's way.

It also buys perceived speed by removing choices rather than accelerating them. A shallow, opinionated hierarchy instead of OmniFocus's infinite nesting. Natural-language date parsing so scheduling is one typed phrase. Soft buckets — "This Evening", "Someday" — that let you file something without deciding much.

The psychological feature

"Someday" is not a list, it's permission. It lets you defer without guilt, which is the actual reason people abandon task systems. Calm is a feature with a mechanism behind it, and the mechanism is subtraction.

What we don't take: Apple-only lock-in and opaque sync. Both conflict directly with the cross-platform bet, and opaque sync is unfixable from the outside when it goes wrong.

No abstraction tax

The principle both cases share

Every framework layer sitting in the critical path leaks perceived latency — a web view, a generic ORM, a network round-trip. Sublime removed the layers by building its own primitives; Things 3 removed the biggest one by never putting the network between a tap and a result. Different tactics, same audit: enumerate what sits between the user's action and the pixel, and delete what doesn't earn its place.

The comparison, stated fairly

Sublime is fast at raw scanning; Obsidian is fast at answering relational questions. Sublime never needs a semantic layer because files are independent — it would be terrible at backlinks, and Obsidian is mediocre at grep. Things 3 sidesteps the question by having far less to be fast about. We are not choosing between them. We are trying to hold the parts that compose.

Rules that follow from the split

1

The index is derived, never source of truth

Files on disk are canonical. The index — in-memory structs, persisted to redb or SQLite as a cache — can be deleted and rebuilt. This is what licenses aggressive caching, and what keeps git and third-party sync working.

2

Atomic objects

One capture equals one file. Edit unit, embed unit, and invalidation unit are the same thing, so re-embedding is cheap by construction rather than by optimisation. No chunking logic, no staleness heuristics, no debounced re-index queue.

3

The latency budget is the architecture

Keystroke-to-pixel under 10ms is a constraint, not a goal. It forbids WebView, JS on the input path, and blocking IO on the UI thread. Indexing, embedding, and sync run off-thread and publish results; the editor never waits.

4

Embeddings flat and local

A ~25MB model, a Vec<[f32; 384]>, brute-force cosine. At 100k objects that is single-digit milliseconds. No vector database, ever.

5

Sync is background, never in the loop

Writes land on local disk and return. Replication happens afterwards, off-thread, and its failure is a state the UI reports rather than a wait the user sits through. This is the Things 3 lesson, and it costs us a conflict-resolution story we have to design deliberately rather than inherit.

6

One object, two facets

A note and a task are the same stored object seen at different moments. Promotion is a frontmatter field appearing — due, status — never a copy into a second store. This is what makes "turn my note into a task without re-typing it" a one-keystroke operation instead of an integration, and it only works because rule 2 already made the object small enough to promote whole.

Precedent: Smart Connections

The Obsidian plugin already proves local-first semantic recall is shipped engineering, not a research bet — transformers.js, a ~25MB BGE model, no API key, fully offline, JSON storage with brute-force cosine similarity. Nobody reaches for a vector DB at vault scale. Below roughly a million vectors, HNSW and hosted indexes solve a problem that doesn't exist.

The weakness we beat structurally

It re-embeds the whole file on any edit — fix a typo in a 2,000-word note and the entire note is re-embedded. That's the background churn users notice as the fan spinning. Rule 2 makes it impossible for us by construction, which is also why it's hard to copy: Obsidian can't adopt atomic objects without breaking file-as-unit.

Where the paywall sits

Smart Connections gives away raw semantic search and charges $60/yr for passive surfacing while you write. Read that as revealed pricing: the market treats access to your own notes as table stakes and won't pay for it. It pays for ranking, relevance, and timing — the judgment layer. So don't gate search. Free tier is genuinely good at "find it when I ask"; paid is "know what I need before I ask". That also happens to be the part that's hard to clone.

And BYOK narrows it further

The brief in Part I says users won't pay a margin on inference they already buy. So the pricing surface shrinks to exactly one thing: the judgment layer, sold on top of a key the user brings or a model that runs locally. Two independent lines of evidence — a competitor's paywall placement and users' stated objection — landing on the same answer is about as much confirmation as this kind of decision ever gets.

Mobile is the open flank

Obsidian mobile is the desktop web codebase in a Capacitor WebView. The symptoms are 60s+ cold starts on large vaults, sync fragility against sandboxed iOS and Android filesystems and iCloud lazy-loading, and roughly 30% of plugins not working because they assume Node APIs or a desktop viewport.

This is architectural, not a backlog item — it follows from "files are the database" meeting a platform that won't hand you the filesystem. Fixing it would require a mobile-specific data layer, which forks their core premise.

The trap to avoid

Wrapped-WebView on mobile is exactly how we would inherit their worst problem while claiming to beat it. Native — or at minimum a native data and index layer under a web UI — is the price of the positioning.

What the surface owes the architecture

Speed the user can feel is not only latency. Things 3 shows that a shallow opinionated hierarchy, natural-language dates, and soft buckets like "This Evening" all reduce the time between intent and a filed object — the same currency as a faster frame, spent on the decision instead of the render.

This also happens to protect rule 2. Atomic objects and a shallow hierarchy reinforce each other: if a capture is one small thing, there is nothing to nest, and the absence of nesting is what keeps invalidation trivial. The calm surface and the fast core are the same decision seen from two sides.

The two risks, named

RiskWhy it bitesMitigation
Plugin ecosystem Obsidian's moat is ~2,000 community plugins. We cannot match it, and parity is not a strategy. Ship the top ten use cases natively; sandbox WASM plugins that talk to the core, never to the UI thread.
Text layout Consistently underestimated. Bidi, ligatures, emoji, IME, soft-wrap with variable fonts. Use an existing engine — cosmic-text, or GPUI's. Do not write our own.

The ledger

Steal

  • Parse once, reuse forever. A bespoke persisted index for the capture-and-retrieval path — Obsidian and Sublime both landed here independently.
  • Open before you index. Usable immediately; features light up as the index fills.
  • Local-first, background sync. The network never sits between a tap and a result.
  • Atomic objects. Edit unit equals embed unit equals invalidation unit.
  • Unfiled is valid. Capture under five seconds means no destination is ever required.
  • One object, two facets. Note becomes task by gaining a field, not by being copied.
  • Calm by subtraction. Shallow hierarchy, NL dates, soft buckets, guilt-free deferral.
  • Flat local embeddings. Brute-force cosine at vault scale; no vector database.

Avoid

  • Wrapped WebView on mobile. Inherits Obsidian's worst problem while claiming to beat it.
  • Custom toolkits early. Sublime bought those years with patient profitability we don't have.
  • Platform lock-in. Things 3's Apple-only bet is closed to us by the cross-platform premise.
  • Opaque sync. Unfixable from the outside when it goes wrong; users blame the app, correctly.
  • Blocking the UI on a full index. A choice, not a requirement.
  • Gating search behind the paywall. The market prices access at zero and judgment at $60/yr.
  • A margin on inference users already buy. BYOK is expected now, not a concession.
  • Knobs as an answer. For the ADHD audience, configurability is the problem wearing a helpful face.

The brief and the machinery agree, which is the useful finding here. Speed is a modelling decision, not an optimisation achievement. Obsidian picked the unit that keeps invalidation small. Sublime deleted every generic layer from the critical path. Things 3 took the network out of the loop entirely and then removed the choices that remained. None of it is a rendering trick — it is three different answers to the same audit of what sits between a user's action and the result. We win by running that audit one level finer (atomic objects), skipping infrastructure that doesn't pay for itself at our scale (vector databases), charging for the layer users actually value (judgment, not access), and refusing the shortcuts that would undo the whole premise (WebView on mobile, opaque sync, custom toolkits we can't afford).
